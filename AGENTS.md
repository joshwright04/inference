# AGENTS.md

## Project Purpose

This repository is an educational C++20 GPU inference engine. The primary goal is
learning, not outsourcing the implementation.

The project should help the developer build deep understanding of:

- modern C++20
- memory management and RAII
- ownership, lifetimes, and move semantics
- computer architecture and performance
- parallel programming
- GPU programming
- CUDA/HIP concepts
- neural-network inference
- profiling and optimization

## Development Environment

The intended environment is:

- Windows
- CLion
- CMake
- Ninja
- C++20
- GoogleTest / CTest
- clang-format
- clang-tidy
- AMD RX 6600
- ROCm/HIP for local GPU execution

The architecture should keep a future CUDA backend reasonable, while the initial
local GPU backend targets HIP/ROCm.

## Collaboration Rules

- Do not implement large portions of the inference engine unless explicitly asked.
- Prefer explanations, design suggestions, code review, and small examples.
- Before implementing a new subsystem, reason through the design and tradeoffs.
- If code works but has poor C++ design, unsafe ownership, unnecessary copies,
  unclear lifetimes, or likely performance problems, point that out and explain why.
- Avoid overengineering. This is a small educational inference engine, not PyTorch.
- Prefer modern, idiomatic C++20 and RAII.
- Keep CPU and GPU functionality separated enough to support additional backends.
- CPU implementations should initially serve as simple correctness/reference
  implementations for GPU operations.
- Tests should verify numerical correctness and important edge cases.
- Correct baseline implementations come before performance optimization.
- When optimizing, explain the bottleneck being targeted and why the optimization
  should help.
- Do not introduce libraries that hide concepts the project is meant to teach
  unless the tradeoff has been discussed.
- Keep CMake and tooling straightforward and maintainable.

## Development Progression

Current progress:

- Basic project structure is in place.
- `TensorShape` exists with tests for rank, element count, scalar shape, empty
  dimensions, and zero-sized dimensions.
- `Tensor` exists with immutable shape metadata and owned CPU `float` storage.
- CPU reference operations exist for elementwise add, ReLU, matrix-vector
  multiply, and naive matrix multiplication.
- CPU operation tests cover ordinary cases, scalar tensors, zero-sized
  dimensions, shape preservation, invalid ranks, incompatible dimensions, and
  input immutability.
- CPU operation validation helpers are file-local implementation details, not
  public API.

The rough remaining progression is:

1. Introduce GPU device and memory abstractions.
2. Write simple HIP GPU kernels.
3. Compare HIP operation results against CPU reference operations.
4. Implement naive GPU matrix multiplication.
5. Implement optimized/tiled matrix multiplication.
6. Add neural-network operators.
7. Add model/layer representation.
8. Load model weights.
9. Execute a small neural network.
10. Profile and optimize.

This progression is provisional. Refine it as the project exposes better
learning steps or cleaner boundaries.

## Code Organization Principles

- Keep public headers small and intentional.
- Separate interface, CPU implementation, and GPU implementation when that
  improves clarity.
- Use RAII wrappers for owning resources such as host buffers, device buffers,
  streams, and events.
- Prefer explicit ownership over raw owning pointers.
- Use raw pointers only for non-owning views or low-level API boundaries where
  the lifetime is documented by the surrounding type.
- Keep numerical tests small, deterministic, and easy to inspect.
- Add performance benchmarks only after the corresponding correctness tests exist.

## Tooling Expectations

- Build through CMake and Ninja.
- Run tests through CTest or the test executable generated by CMake.
- Keep formatting automated with clang-format.
- Use clang-tidy once it is available in the local toolchain.
- Keep generated build directories out of source control.
